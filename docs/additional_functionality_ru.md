# Добавочный функционал ServerFlow (расширение к релизному контуру)

> [!WARNING]
> Этот документ описывает **планируемый** функционал (roadmap), который ещё **не реализован** в коде.
> Система пресетов (`ScenarioProfileDefinition`, `ProfileRegistry`, `ProfileManager`) в текущей версии отсутствует.

## 1) Цель документа

Зафиксировать требования к **расширяемому каталогу режимов и пресетов**, чтобы:
- сервер управлялся через один runtime-поток (единый старт + ServerFlow);
- новые режимы/карты/варианты режимов добавлялись без правки ядра;
- администратор мог безопасно выбирать не только режим, но и профиль (preset) режима.

---

## 2) Текущее положение и стадия

Проект находится на стадии **stabilization / pre-release**:
- базовая state-driven архитектура уже собрана;
- есть pipeline pending/confirm/apply;
- есть сценарии и плейлисты;
- но нет полной продуктовой матрицы стандартных режимов CS:GO и отсутствует слой пресетов режима как first-class сущность.

Это означает: фундамент есть, до релиза нужен фокус на completeness + operability + docs quality.

---

## 3) Что нужно довести до релизного уровня

### 3.1 Каталог режимов (scenario catalog)
Минимум для релизной полноты:
- покрыть стандартные игровые направления (casual/competitive/wingman/armsrace/demolition/deathmatch/training и т.д.);
- для каждого сценария явно зафиксировать `game_type`, `game_mode`, `mapgroup`, `start_map`, `playlist_id`, политику maplist;
- добавить практичные примеры для workshop/custom map pools.

### 3.2 Пресеты режима (mode profiles)
Нужен отдельный конфиг-слой над сценарием:
- `profile_id`, `scenario_id`, `title`, `description`, `cfg_file`, optional overrides;
- выбор профиля перед запуском сценария;
- валидация: профиль не может ссылаться на несуществующий сценарий;
- fallback: при ошибке профиля запускать базовый профиль сценария.

Пример применения:
- Arms Race default;
- Arms Race pistols-only;
- Arms Race heavy-finale.

### 3.3 UX и операторский контур
- в меню/командах должно быть видно: **текущий сценарий**, **очередной сценарий**, **очередной профиль**, **когда применится**;
- ошибки конфигов должны быть человеко-читаемыми;
- гайд «как добавить режим/карту/профиль» обязателен и должен содержать copy-paste примеры.

---

## 4) Целевая модель данных (расширение)

Добавить сущность `ScenarioProfileDefinition` (или аналог):
- `id` (string)
- `scenarioId` (string)
- `namePhrase/title` (string)
- `cfgFile` (string)
- `rulesetRef` (optional string)
- `isDefault` (bool)

И поддержать:
- `ProfileRegistry` (lookup/validation)
- `ProfileManager` (selection/apply policy)
- runtime-поле в сессии: `currentProfile`, `queuedProfile`.

---

## 5) Стратегия внедрения (по шагам)

1. **Stability pass**
   - чистка репозитория от нерелевантного шума;
   - запрет source-mutation в build;
   - единый стартовый bat.

2. **Scenario completeness pass**
   - расширение `scenarios.cfg` и `playlists.cfg`;
   - примеры стандартных режимов и workshop-пулов.

3. **Profile layer pass**
   - новые конфиги профилей;
   - загрузка/валидация профилей;
   - команды выбора профиля + pending pipeline.

4. **Operator docs pass**
   - отдельные инструкции «добавить режим», «добавить карту», «добавить профиль»;
   - troubleshooting разделы.

---

## 6) Критерии готовности к релизу

Релиз считается готовым, если:
- нет критических ошибок в health-check при старте и смене карты;
- конфиги валидируются и дают понятные ошибки;
- оператор может без кода добавить новый сценарий и новый профиль;
- runtime-переходы сценарий/профиль выполняются только через безопасный pending/apply pipeline;
- документация покрывает все операционные сценарии.

---

## 7) Почему это важно

Без слоя пресетов и подробных операторских инструкций проект остаётся «работающим прототипом». 
С этим слоем проект становится **профессиональной платформой управления сервером**: расширяемой, предсказуемой и безопасной для эксплуатации.
