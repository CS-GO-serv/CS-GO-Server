# AGENTS.md

## Назначение

Этот репозиторий содержит конфиги и код для серверного плагина CS:GO Legacy на SourceMod.

Твоя задача как агента — не просто написать рабочий код, а построить **надёжную, расширяемую и понятную систему управления сервером**, которая:

- управляет сценариями игры;
- управляет картами и playlist;
- ведёт сервер через состояния Lobby / PreMatch / Match / PostMatch / Transition;
- работает с ready-check, countdown, AFK, late join, squads, голосованиями и admin override;
- не ломается от расширения и новых сценариев.

Главное правило: **качество архитектуры важнее скорости первой рабочей версии**.

---

## Что это за проект

Это **не просто mode vote plugin**.

Это:
- state-driven server flow manager;
- scenario-driven system;
- config-driven gameplay controller;
- safe transition pipeline between server states.

Если твоё решение выглядит как “ещё одно текстовое меню для админа”, значит ты понял задачу неправильно.

---

## Главный принцип

Всегда думай так:

1. В каком состоянии сейчас сервер?
2. Что является текущим сценарием?
3. Что выбрано следующим?
4. Когда это должно примениться?
5. Безопасно ли применять это сейчас?
6. Как игрок увидит, что происходит?

Никогда не думай только в терминах:
- `вызвали команду`
- `показали меню`
- `сразу применили cfg`

Сначала состояние и правила. Потом применение. Потом UI.

## Обязательная модель мышления

Перед реализацией любой фичи всегда проходи этот порядок:

### 1. Понять место фичи в state machine
Спроси себя:
- это работает в Lobby, PreMatch, Match, PostMatch или Transition?
- это безопасное действие или только queued action?
- это immediate action или pending + confirm?

### 2. Понять, к какому слою относится изменение
- core
- runtime
- config
- domain
- presentation
- commands
- diagnostics
- integrations

### 3. Проверить, нельзя ли решить это через уже существующий модуль
Не дублируй логику.

### 4. Только потом писать код

## Что запрещено делать

### Архитектурные запреты

Нельзя:
- писать монолитный `.sp` файл, в котором всё сразу;
- размазывать правила сценариев по десяткам `if/else`;
- напрямую менять карту из menu callback;
- напрямую применять cfg из chat command handler;
- менять состояние сервера в обход StateManager;
- применять сценарий в обход TransitionManager;
- хранить альтернативные копии runtime-state в нескольких местах;
- смешивать UI и бизнес-логику;
- дублировать одну и ту же логику countdown / ready / vote в разных файлах.

### UX-запреты

Нельзя делать основной UX как:
- сырое техничное SourceMod-меню без смысла;
- показ внутренних cfg/aliases/enum игроку;
- интерфейс, который ощущается как админская утилита, а не игровая система.

Если игрок видит технические термины вместо игровых решений, UX плохой.

### Качество-запреты

Нельзя:
- молча глотать ошибки;
- silently fail;
- оставлять невалидное состояние без fallback;
- создавать хрупкие решения “лишь бы работало сейчас”;
- использовать магические строки и числа без констант или конфигов;
- писать конфиги без комментариев.

---

## Что обязательно делать

### Архитектурно

Всегда:
- используй state machine;
- используй single source of truth для runtime-state;
- используй config-driven scenarios и playlists;
- пропускай все важные действия через pending/confirm/apply pipeline;
- применяй критические изменения только через TransitionManager;
- логируй все важные события;
- делай fallback to Lobby при опасных ошибках.

### Для UX

Всегда:
- показывай игрокам, что происходит;
- показывай, что выбрано следующим;
- показывай, когда это применится;
- показывай, почему матч ещё не стартует;
- делай важные изменения видимыми и предсказуемыми.

### Для конфигов

Всегда:
- выноси параметры в конфиги, если они могут понадобиться для настройки;
- снабжай параметры комментариями;
- валидируй конфиги при загрузке;
- делай ошибки конфигов понятными для человека.

## Приоритеты проекта

Если приходится выбирать, что важнее, следуй такому приоритету:

1. Безопасность переходов состояния
2. Прозрачность происходящего для игроков
3. Расширяемость архитектуры
4. Предсказуемость поведения
5. Качество конфигов
6. Удобство UI
7. Скорость реализации

То есть:
- лучше медленнее, но правильно;
- лучше проще, но архитектурно чисто;
- лучше staged implementation, чем быстрое хрупкое решение.

---

## Как принимать решения по реализации

### Если есть выбор между быстрым и правильным решением
Выбирай правильное.

### Если есть выбор между красивым UI и безопасной логикой
Сначала делай безопасную логику.

### Если есть выбор между жёстко прошитым режимом и data-driven scenario
Выбирай data-driven scenario.

### Если есть выбор между “сейчас сразу применить” и “поставить в очередь через pending change”
По умолчанию выбирай pending change.

### Если есть сомнение, можно ли менять что-то во время Match
Считай, что нельзя, пока нет безопасного явно описанного исключения.

## Обязательная архитектура слоёв

Используй именно слоистую архитектуру.

### Core
Общие enum, типы, константы, helper-функции.

### Runtime
Session store, state machine, transition pipeline, pending change.

### Config
Загрузка и валидация core/scenarios/playlists конфигов.

### Domain
Игровая логика: scenarios, playlists, players, ready, countdown, teams, votes, admin override.

### Presentation
Показ статуса, уведомлений, меню и интерактивных экранов.

### Commands
Маршрутизация команд в доменную логику.

### Diagnostics
Health check, audit log, state dump.

### Integrations
Hooks в игровые события, map control, client lifecycle, timers.

Если ты ловишь себя на том, что command handler принимает архитектурное решение — это плохой знак.

## Правила по состояниям

### Lobby
Можно:
- выбирать следующий сценарий;
- запускать голосования;
- ставить queued admin actions;
- безопасно менять планы.

### PreMatch
Можно:
- показывать preview выбранного сценария;
- собирать команды;
- ждать ready;
- запускать countdown;
- отменять старт по валидным причинам.

### Match
Нельзя:
- ломать текущий матч обычными действиями;
- мгновенно менять режим без emergency override.

Можно:
- выбирать следующее действие;
- ставить pending changes;
- показывать status.

### PostMatch
Можно:
- показать итог;
- предложить следующий шаг;
- собрать решение;
- провести confirm window;
- уйти в Transition.

### Transition
Должен:
- только применять уже подтверждённое решение;
- валидировать всё перед применением;
- уметь fallback в Lobby.

---

## Правила для pending / confirm / apply

Никогда не применяй важные решения мгновенно, если это не emergency override.

Правильный pipeline:

1. Proposal
2. Selected
3. Confirmed
4. Applying
5. Applied

Игроки должны успевать увидеть:
- что выбрано;
- кем выбрано;
- когда применится;
- можно ли ещё отменить.

---

## Правила для ready и countdown

Ready и countdown — это не косметика, а часть критической логики старта.

### Обязательно:
- ready должен считаться из player runtime state;
- countdown должен запускаться только при выполнении всех условий;
- countdown должен сбрасываться, если условия ломаются;
- причина сброса должна быть видна игрокам;
- после countdown должна быть lock phase.

### Запрещено:
- хранить ready count вручную, не пересчитывая состояния игроков;
- стартовать матч просто потому, что истёк таймер, игнорируя правила сценария;
- делать countdown “одним таймером где-нибудь в меню”.

---

## Правила для AFK и late join

### AFK
AFK не должен бесконечно блокировать матч.

Нужно:
- отдельное отслеживание AFK;
- отдельная политика сценария по AFK;
- исключение из ready-pool или перевод в spectator по правилам.

### Late join
Нужно поддерживать:
- soft late join;
- hard late join.

Если countdown уже идёт и приходит новый eligible игрок:
- при soft policy countdown сбрасывается;
- при hard policy игрок идёт в spectator до safe-point.

Никогда не оставляй late join “как получится”.

---

## Правила для команд и squad logic

### Нельзя
- стартовать командный сценарий без проверки валидности состава;
- считать, что игрок “как-нибудь разберётся” без server-side validation.

### Нужно
- отдельный TeamManager;
- team policies: auto, open, captain, keep previous, autofill leftovers;
- strict/soft validation;
- понятные причины, почему старт сейчас невозможен.

---

## Правила для голосований

VoteManager должен быть отдельной системой.

### Нельзя
- считать голосование просто “меню, которое сразу меняет режим”;
- напрямую применять результат голосования;
- допускать бесконечный спам vote.

### Нужно
- lifecycle голосования;
- cooldown;
- quorum;
- minimum players;
- tie-break policy;
- visible result;
- перевод результата в pending change.

---

## Правила для админа

Админ — это и игрок, и оператор сервера.

### Админ должен иметь
- обычный player UX;
- отдельный admin layer.

### Админ может
- queue next scenario;
- queue next map;
- force lobby;
- cancel pending;
- restart current scenario;
- lock votes;
- unlock votes;
- run health check;
- делать override разного уровня.

### Но даже админ не должен
- ломать state machine;
- применять невалидный сценарий;
- применять невалидную карту;
- обходить логирование;
- случайно оставлять сервер в поломанном состоянии.

Если админское действие опасно — оно должно идти через safe override или emergency override с явным логом.

---

## Как проектировать UI

### Главное правило
UI — это слой представления, а не место принятия решений.

### Нельзя
- проектировать систему от меню вниз;
- лепить бизнес-логику внутрь callback-ов меню;
- строить UX только на технических текстовых списках без стадийности.

### Нужно
- сначала реализовать логику и state machine;
- потом делать UI поверх неё;
- на каждом экране давать игроку только одно понятное решение;
- использовать игровые, а не технические формулировки.

### Игрок должен видеть
не `apply profile` и `router alias`, а:
- `Solo / Duo / Trio`
- `Авто-команды / Собираем сами`
- `Следующая карта`
- `В Lobby`
- `Старт через 10 секунд`
- `Старт отменён: подключился новый игрок`

## Как писать новые фичи

Перед реализацией новой фичи всегда делай короткую внутреннюю проверку:

1. К какому состоянию относится эта фича?
2. Это часть runtime, domain или presentation?
3. Есть ли уже модуль, где это должно жить?
4. Не дублирует ли это существующую логику?
5. Нужен ли для этого новый config parameter?
6. Должно ли это быть видно игрокам?
7. Что будет, если это сломается?
8. Какой должен быть fallback?

Если ты не можешь ответить на эти вопросы, не пиши код вслепую.

## Как обновлять проект

При добавлении новой возможности:

1. Сначала обнови data model / enums / config schema при необходимости.
2. Потом добавь runtime/domain-логику.
3. Потом интегрируй в state machine.
4. Потом добавь status visibility.
5. Потом добавь UI / commands.
6. Потом добавь health-check и логирование.

Не делай наоборот.

## Работа с конфигами

Все конфиги должны быть:
- понятными;
- редактируемыми людьми;
- снабжёнными комментариями;
- валидируемыми при загрузке.

Если параметр может разумно понадобиться админам сервера, его лучше вынести в конфиг.

Особенно это касается:
- таймеров;
- процентов;
- лимитов;
- AFK timeout;
- late join policy;
- vote cooldown;
- confirm window;
- team validation behavior;
- postmatch default action.

---

## Работа с ошибками

Никогда не скрывай ошибку, если она влияет на серверную логику.

### При любой важной ошибке нужно:
1. записать её в лог;
2. показать понятное сообщение, если это затрагивает игроков или админа;
3. отменить опасное действие;
4. вернуть сервер в safe-state, если нужно.

### Safe-state по умолчанию
`Lobby`

Если ты не уверен, что делать после ошибки, предпочитай безопасный fallback в Lobby.

## Обязательные проверки качества перед завершением задачи

Перед тем как считать задачу завершённой, проверь:

- используется ли правильный слой архитектуры;
- нет ли дублирования состояния;
- не делается ли переход в обход TransitionManager;
- логируется ли ключевое событие;
- видят ли игроки, что происходит;
- есть ли fallback;
- есть ли комментарии в новых конфигурациях;
- можно ли расширить решение без переписывания ядра.

---

## Что считать хорошим решением

Хорошее решение в этом репозитории — это решение, которое:
- понятно читается;
- разделено по слоям;
- не ломается при расширении;
- объяснимо для другого разработчика;
- уважает state machine;
- прозрачно для игроков;
- безопасно для админа;
- не требует переписывать половину проекта ради новой фичи.

---

## Что считать плохим решением

Плохое решение — это решение, которое:
- быстро работает, но архитектурно грязное;
- напрямую меняет карту/режим из меню;
- не имеет pending/confirm слоя;
- не учитывает late join и AFK;
- не объясняет игрокам, что происходит;
- жёстко прошивает сценарии в коде;
- размазывает состояние по всему проекту;
- не имеет fallback и диагностики.

---

## Итоговая рабочая установка

Всегда помни:

Этот проект нужно делать как **профессиональную серверную систему**, а не как “ещё один vote plugin”.

Правильный порядок мышления такой:

**State -> Scenario -> Validation -> Pending -> Confirm -> Transition -> Visibility -> UI**

А не:

**Menu -> Command -> Random cfg -> Hope it works**

Если придерживаться этого AGENTS.md, проект не скатится в плохие решения и останется расширяемым, понятным и надёжным.
